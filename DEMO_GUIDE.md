# Как открыть сайт и показать CMS на защите

## Что сейчас работает

Сервер API (порт 3001) и frontend (порт 5173) запущены в облачной машине. Главная, административный маршрут и API отвечают HTTP 200. В базе 58 записей; SQLite integrity_check — ok.

Адреса **в браузере облачной машины**:

- Публичная часть: `http://localhost:5173/`.
- Словарь: `http://localhost:5173/dictionary`.
- Матрёшка: `http://localhost:5173/dictionary/matryoshka`.
- Административная панель: `http://localhost:5173/admin`.

Это не опубликованный интернет-сайт. На вашем Mac адрес localhost указывает на Mac, а не на облачную машину. В этом сеансе нет инструмента выдачи внешней ссылки/проброса порта и управления облачным браузером. Если интерфейс Codex предлагает Desktop, откройте браузер внутри него и используйте адреса выше. Для запуска непосредственно на Mac используйте инструкции в ADMIN_GUIDE.md: установка зависимостей и запуск двух процессов создадут отдельную локальную копию сайта и базы.

## Создание личного владельца

Владелец входит **только по паролю**. Придумывать email или логин не нужно. Личная запись в рабочей базе пока не создана.

Откройте доверенный терминал **той машины, где работает сайт**. Для текущей облачной машины вставьте:

```bash
cd /workspace/russkiy-sled
bash scripts/create-owner.sh
```

1. Подготовьте уникальный пароль длиной 14–256 символов и сохраните его в менеджере паролей.
2. Введите пароль по запросу и нажмите Enter. Буквы и звёздочки не отображаются — это нормально.
3. Введите тот же пароль повторно и нажмите Enter.
4. Дождитесь сообщения «Владелец создан». При несовпадении паролей ничего не создаётся. При слишком коротком пароле команда откажет, её можно запустить заново.
5. Откройте `/admin`, введите выбранный пароль и нажмите «Войти».
6. Успешный вход покажет «Редакция словаря», обзор базы и кнопку «Выйти».
7. Перезагрузите страницу: список останется доступен, пока сессия не истечёт (8 часов).

Команда работает один раз для выбранной базы и не перезаписывает существующего владельца. Пароль не попадает в текст команды, Git или файл настроек; в SQLite сохраняется его хеш. Не присылайте пароль в чат. Запуск этой команды на Mac не создаст владельца в облачной базе.

Если используется нестандартный CMS_DB_PATH, передайте тот же путь при создании владельца, запуске сервера и создании копий. При обычном запуске ничего задавать не нужно. После создания владельца сервер перезапускать не требуется.

## Репетиция редактирования — без изменения научных фактов

1. Войдите в административную панель.
2. Перейдите в «Словарь», найдите «Матрёшка» и откройте её статью.
3. Нажмите «Редактировать статью» на панели владельца.
4. В разделе «Основная информация» запомните исходное содержимое поля «Редакционное примечание».
5. Добавьте к нему отдельной строкой: «Демонстрация CMS: проверка сохранения».
6. Внизу выберите **редакционный** статус «Опубликовано». Научные статусы не меняйте.
7. Нажмите «Сохранить изменения», подтвердите публикацию и дождитесь «Версия сохранена. Опубликовано».
8. Нажмите «Открыть статью» — на ней появится примечание.
9. Обновите страницу браузера. Примечание должно остаться: оно хранится в SQLite.
10. Для проверки обычного посетителя откройте статью в приватном окне того же браузера. Примечание видно, панели владельца нет.
11. Вернитесь в редактор и восстановите исходное содержимое примечания. Снова сохраните со статусом «Опубликовано» и подтвердите действие.
12. Нажмите «Выйти»: панель редактирования исчезнет. Для нового входа понадобится ваш пароль.

Если сохранить как черновик, публичная версия прежней статьи останется прежней — это ожидаемое поведение. При ошибке сохранения не закрывайте форму: исправьте причину и повторите сохранение. Не демонстрируйте правки транскрипций, дат или научных выводов ради проверки кнопок.

## Где база и как сохранить копию

Рабочая база облачной машины: `/workspace/russkiy-sled/.cms/content.sqlite`.

Сайт читает именно эту SQLite-базу. Перезагрузка страницы и перезапуск сервера её не удаляют. `.cms/` исключён из Git: сохранение кода не заменяет копирование базы. Временную облачную машину также нельзя считать внешним резервным хранилищем.

Проверенная копия до создания личного владельца уже сохранена:
`/workspace/russkiy-sled-backups/before-owner-2026-11-15.sqlite`.
Она содержит 58 записей, проходит проверку целостности и имеет права 0600. Личного владельца в ней ещё нет.

После создания владельца и перед защитой выполните новую копию. Из терминала облачной машины:

```bash
cd /workspace/russkiy-sled
mkdir -p -m 700 /workspace/russkiy-sled-backups
npm run db:backup -- /workspace/russkiy-sled-backups/before-defense.sqlite
```

Для следующей копии выберите другое имя файла: команда специально не перезаписывает старые копии. Сервер можно оставить работающим. Не копируйте один content.sqlite обычной командой cp во время работы: SQLite использует дополнительные WAL-файлы, а db:backup делает согласованную копию.

Копию скачайте и храните отдельно от облачной машины, например на своём Mac и дополнительном носителе. Она содержит непубличные черновики, хеш пароля и сессии — не публикуйте её и не отправляйте в Git. Восстановление с отзывом старых сессий описано в ADMIN_GUIDE.md.

На Mac из каталога проекта вместо облачного пути можно использовать:

```bash
mkdir -p -m 700 "$HOME/russkiy-sled-backups"
npm run db:backup -- "$HOME/russkiy-sled-backups/before-defense.sqlite"
```

## Что проверено, а что требует вашего действия

На отдельной временной базе проверены интерактивная команда создания владельца, отказ при несовпадающих паролях, запрет повторного создания, вход через настоящий интерфейс, сохранение сессии при перезагрузке, открытие редактора статьи и выход. Тестовый пароль генерировался автоматически, не показывался и удалён вместе с тестовой базой.

Ваш личный вход не проверен: сначала вы должны задать свой пароль через команду выше. Личный пароль не выбирался и рабочая учётная запись автоматически не создавалась. Второй этап CMS не начат.
