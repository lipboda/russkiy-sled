# Безопасное обновление CMS на MacBook: второй этап

Ветка: **feat/cms-stage2**, основана на **release/cms-stage1-macbook**. Первая версия сохранена. Не удаляйте `.cms/`, не запускайте повторно создание владельца и не заменяйте свою SQLite файлом из облака. Исходные 58 записей не импортируются повторно в существующую базу.

## Обновление через GitHub Desktop

1. Остановите **оба своих процесса**: в окне API и в окне Vite нажмите **Control+C**. Убедитесь, что это окна проекта. Safari можно оставить открытым.
2. Пока выбрана старая ветка, откройте терминал в корне проекта через Repository → Open in Terminal и сделайте резервную копию:

```sh
mkdir -p -m 700 "$HOME/russkiy-sled-backups"
npm run db:backup -- "$HOME/russkiy-sled-backups/before-stage2.sqlite"
```

Если файл уже существует, выберите другое имя. Копия не перезаписывается. Если вы используете собственный `CMS_DB_PATH`, передайте **тот же путь**, который использует ваш API, и при резервировании. Дождитесь «Резервная копия создана». По возможности сохраните копию также на другом носителе.

3. В GitHub Desktop сохраните свои незакоммиченные правки кода, если они есть. Не используйте Discard Changes. Нажмите **Fetch origin → Current Branch → feat/cms-stage2**, затем Pull origin, если он предложен. `.cms/` исключена из Git и остаётся на Mac при переключении ветки.
4. В корне проекта выполните:

```sh
node --version
npm --version
npm ci
npm run db:migrate
npm run build
```

Нужны Node.js **24.22+ ветки 24** и npm (проверено с 11.9.0). `.nvmrc` содержит 24.22.1. Если пользуетесь nvm — сначала `nvm install && nvm use`. Внешние ключи, Supabase и Docker не требуются. `npm ci` использует обновлённый lockfile; не запускайте `npm audit fix --force`.

5. При первой миграции перед изменением схемы автоматически создаётся дополнительная согласованная копия старой базы в **`backups/` рядом с файлом SQLite**, по умолчанию `.cms/backups/before-stage2-….sqlite`. Используется VACUUM INTO с учётом WAL; если копию создать нельзя, миграция не продолжается. Копия имеет права 0600. Миграция выполняется транзакционно и отмечается номером 2; повторный запуск не заменяет данные. Владелец, сессии, идентификаторы, словарные правки, статусы и история первого этапа сохраняются. Сам `db:backup` в новой ветке открывает существующую базу только для чтения и **не запускает миграции**.
6. Запустите API в первом окне:

```sh
npm run server
```

Во втором окне терминала, в той же папке проекта:

```sh
npm run dev -- --port 5173 --strictPort
```

7. Откройте в Safari **http://localhost:5173/admin** и войдите **с прежним паролем**. Создавать нового владельца не нужно. Главная: **http://localhost:5173/**. Используйте localhost, не меняя его на 127.0.0.1. Проверка доступности в Linux не заменяет репетицию в настоящем Safari на Mac.

## Что появилось

- Навигация CMS: обзор, словарь, категории, исследование, журнал, слово дня, источники, медиатека, корзина, история, настройки.
- Словарь: однострочная лемма, скрытый технический ID, закреплённая кнопка сохранения, отмена, предпросмотр, дублирование, черновик, публикация, снятие с публикации, архив, корзина, восстановление и окончательное удаление с проверкой связей. Есть выбор нескольких записей для публикации/архивирования/корзины и назначения категории. Назначение категории пакетно редактирует черновики, а не публикует незавершённые изменения.
- Категории: поиск и множественный выбор в статье, теги и создание из списка; отдельный редактор названия, описания и порядка, подсчёт связей, объединение и удаление без удаления статей. Переименование отражается и в публичных снимках. Версии затронутых слов повышаются, чтобы открытый устаревший редактор не вернул прежнее название категории.
- Языковые карточки: независимое редактирование, скрытие, перестановка и удаление. Настройки позволяют добавлять языки и страну; три исходных языка остаются основными для исследования. Научные статусы включают «Подтверждено», «Частично подтверждено», «Предположительно» и «Не установлено», сохраняя прежние статусы и проверки доказательств.
- Журнал: три прежние статьи мигрируют с теми же URL и содержанием. Создание, редактирование, копия, предпросмотр Markdown, обложка, автор, дата, источники, связи со словами, черновики, публикация, планирование, архив/корзина. В публичном архиве — поиск, категория, месяц публикации.
- «Слово дня»: отдельные редакционные выпуски, заполнение из статьи без генерации фактов, тексты происхождения/адаптации/примеров, обложка и источники; календарь, перенос даты, черновики, публикация, планирование, архив/корзина. Самостоятельный выпуск может не иметь связанного слова. Редакционная публикация не повышает научный статус связанного слова.
- Публичный архив выпусков: **/word-of-the-day/archive**, поиск, месяц/год, отдельные страницы и переходы между соседними выпусками. Постоянный адрес **/word-of-the-day/issue/URL** сохраняется при переносе даты; адрес по дате также доступен. Если на сегодня выпуска нет, показывается последний опубликованный с его реальной датой. В старой версии опубликованных выпусков не было: миграция их не придумывает.
- Источники: единый справочник с метаданными и выбором/созданием из редактора. Дата верификации устанавливается только после вашей независимой проверки и не меняет статусы форм автоматически. Используемый источник нельзя удалить: сначала нужно явно убрать ссылки.
- Медиатека: PNG/JPEG/WebP до 5 МБ и 20 млн пикселей. Сервер декодирует изображение, удаляет исходные метаданные и сохраняет неподвижный WebP. Есть alt, подпись, авторство, источник, повторное использование и изменение описания. SVG и анимация не принимаются. Изображения хранятся в SQLite и входят в db:backup.
- История: прежние версии словаря и новые события словаря/журнала/выпусков, просмотр предыдущей и новой версии, восстановление предыдущей в черновик. Корзина восстанавливает материалы в черновики. Окончательное удаление не стирает журнал аудита и не удаляет связанные материалы.
- Сравнение: кнопка открывает языковые карточки соответствующего слова в едином редакторе. Отдельных копий транскрипций и значений нет. Основной набор из восьми слов и их порядок сохранены.

## Как пользоваться планированием

В «Настройках» укажите часовой пояс IANA, например **Asia/Novosibirsk**, Europe/Moscow или Asia/Yerevan. По умолчанию — Asia/Novosibirsk. Эта настройка относится к проекту, а не к системному времени Mac.

В журнале задайте время публикации в поле с поясом проекта и выберите «Запланировано». Интерфейс преобразует выбранное местное время в абсолютный момент. В выпуске «Слово дня» можно задать только дату: он станет доступен с начала соответствующей даты в поясе проекта; дополнительное время задаёт более поздний порог. Два активных выпуска на одну дату не допускаются; несколько черновиков допустимы. Для замены уже активного выпуска сначала явно снимите его с публикации/архивируйте, затем опубликуйте другой.

Публикация определяется при чтении API. Отдельный cron и постоянно работающая фоновая задача не нужны. Mac и API должны работать, когда посетитель открывает сайт. Уже открытая вкладка обновляет данные при навигации, возвращении фокуса или перезагрузке; постоянного push-канала и автоматического обновления ровно в полночь нет. Изменение часового пояса меняет границу дня у выпусков, но уже сохранённое точное время публикации остаётся тем же абсолютным моментом: при необходимости пересохраните его вручную.

## Короткая проверка после обновления

1. Войдите прежним паролем, найдите свою ранее изменённую статью. Проверьте её текст, армянские формы, IPA, URL и прежнюю историю. Количество слов должно соответствовать вашей базе: исходно 58, плюс ваши собственные добавления.
2. Создайте черновик и категорию, переименуйте категорию. Проверьте связь, дублирование, корзину и восстановление. Проверку окончательного удаления выполняйте только на ненужном тестовом черновике.
3. Откройте старую статью журнала `/journal/how-to-read`, затем создайте тестовую заметку, проверьте Markdown-предпросмотр, публикацию и приватное окно Safari.
4. Создайте два выпуска на разные прошедшие даты с явной пометкой «Тест интерфейса — не научный материал». Проверьте архив и соседние выпуски. Запланируйте будущий выпуск: в приватном окне до срока его не должно быть видно. После проверки уберите тестовые публикации в корзину.
5. Загрузите разрешённое изображение с alt, выберите его в публикации. Попытка удалить используемое изображение должна быть отклонена.
6. Проверьте редактирование через сравнение и перезагрузку страницы. Для демонстрации меняйте редакционное примечание, не научные факты.
7. Остановите/запустите API и убедитесь, что данные сохранились. Затем сделайте свежую резервную копию с новым именем.

## Откат при ошибке

**Не удаляйте текущую базу и не откатывайте её поверх работающего API.**

1. Остановите API и Vite Control+C. Сохраните текущее состояние командой db:backup в отдельный файл, например `after-stage2-for-recovery.sqlite`, чтобы не потерять изменения, сделанные после обновления.
2. В GitHub Desktop переключитесь на **release/cms-stage1-macbook**. Ваши изменения кода предварительно сохраните, не используйте принудительный сброс.
3. В корне проекта подготовьте **новый** файл из ручной копии до миграции:

```sh
test ! -e .cms/rollback-stage1.sqlite && cp "$HOME/russkiy-sled-backups/before-stage2.sqlite" .cms/rollback-stage1.sqlite
chmod 600 .cms/rollback-stage1.sqlite
```

Если файл уже существует, не перезаписывайте его — выберите другое новое имя и используйте его во всех следующих командах. Можно взять автоматическую копию из `.cms/backups/`, созданную непосредственно перед миграцией, вместо ручной копии. Не копируйте файлы `-wal` и `-shm` от другой базы.

4. Проверьте восстановленную базу и отзовите старые сессии **только в восстановленной копии**:

```sh
CMS_DB_PATH="$PWD/.cms/rollback-stage1.sqlite" node --input-type=module -e 'import {DatabaseSync} from "node:sqlite"; const db=new DatabaseSync(process.env.CMS_DB_PATH); const r=db.prepare("PRAGMA integrity_check").get(); if(r.integrity_check!=="ok") throw new Error("База повреждена"); db.exec("DELETE FROM sessions; DELETE FROM attempts"); db.close(); console.log("ok");'
```

5. После результата `ok`:

```sh
npm ci
npm run build
export CMS_DB_PATH="$PWD/.cms/rollback-stage1.sqlite"
npm run server
```

Во втором окне запустите Vite обычной командой. Войдите своим прежним паролем. При каждом новом запуске после отката **явно задавайте этот же CMS_DB_PATH** API и командам резервирования. Без него API откроет `.cms/content.sqlite`, где остаётся база второго этапа.

Код первого этапа не умеет отображать новые разделы; для корректного отката требуется именно копия **до** миграции. Первоначальная база второго этапа остаётся нетронутой. Новые данные этапа 2 не появляются в старой резервной копии — для их сохранения не удаляйте копию after-stage2-for-recovery.sqlite и перед последующим возвратом ко второму этапу выберите нужную актуальную базу явно.

## Проверки и ограничения

Автоматические проверки выполняются в Linux с Chromium, не в реальном Safari. Формы публичных предложений и ошибок по-прежнему скачивают TXT, не отправляют сообщения. Нового визуального конструктора главной, редактирования геометрии карты и импорта исследовательских PDF этот этап не добавляет. Админ-панель имеет собственную навигацию; Markdown — редактор с предпросмотром, а не WYSIWYG. История сравнивает JSON-снимки рядом, а не выделяет каждое изменённое слово. Категории в словаре — общий связанный справочник; категория журнальной публикации — самостоятельная текстовая метка для публичного фильтра.

Удаление слова, связанного с исследованием, другой статьёй, журналом или выпуском, блокируется до явного удаления связей владельцем. Не стираются источники или языковые карточки других материалов. Прямые URL изображений публичны; приватные документы в медиатеку не загружайте. Размер основного JS-пакета пока вызывает предупреждение Vite; это не ошибка сборки. Зависимости и их аудит описаны в SECURITY_DEPENDENCIES.md.
