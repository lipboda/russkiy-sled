# Финальное наполнение «Русского следа»

После успешного импорта и нового явного разрешения владельца на публикацию всех 28 слов используйте [финальную команду публикации](FINAL_DEMO_GUIDE.md): `npm run content:publish-final`. Повторять импорт не нужно.

Для локальной базы с 21 защищённой записью и 7 отсутствующими словами используйте [режим согласованного обновления](IMPORT_REVIEW_GUIDE.md): он показывает различия по полям и требует явного подтверждения владельца. Обычный импорт ниже сохраняет прежнюю защиту.

Работа выполнена в согласованной ветке `feat/homepage-editorial-redesign`, поверх главной страницы, карты и этапа 3 CMS. Архитектура, авторизация, схема SQLite, исходные PDF и стартовый каталог не заменяются. Новый файл сохранён побайтно: `research/imports/russkiy-sled-content-final.json`. Старый незавершённый JSON импортёр по умолчанию не использует и его формат не принимает.

## Что перенесено

- 8 основных статей, 24 исследовательские языковые карточки.
- 20 дополнительных кратких статей, 40 иностранных форм.
- 9 языков, 9 опорных стран, 14 категорий, 65 источников.
- Четыре направления адаптации в полях графики, фонетики, семантики, грамматики; пять критериев освоенности и итог карточки — в поле «Степень освоения»; сравнительный вывод — в исследовательском примечании статьи.
- `languageCards[].foreignForm` и `foreignForms[].writtenForm` становятся `languages[].reportedForms`. Коды `fr` → `fr-FR`, `hy` / `hy-EA` → `hy-AM`. Идентификаторы и коды остальных языков согласованы с их опорными странами.
- Полный исходный JSON, включая `sourceTableCells`, `originalResearchCard`, первоначальные статусы и общие научные выводы, хранится в исходном файле и закрытой записи `import-package` журнала SQLite. Эти объекты не копируются в обычный публичный текст. Исходники PDF и прежний аудит остаются на месте.

Все 28 сохраняются с редакционным статусом **«Черновик»**. Научные поля отдельно: `publicationStatus=provisional`, `scientificStatus=pending`, формы `attestationStatus=pending`, тип соответствия `unknown`. Это разные статусы. Заявление составителя JSON о проверке источника сохраняется как происхождение данных, но не превращается автоматически в `verifiedAt` или подтверждённое заимствование.

## Обновление MacBook и импорт

1. В GitHub Desktop сохраните свои изменения кода, нажмите **Fetch origin**, выберите `feat/homepage-editorial-redesign`, затем **Pull origin**, если доступно. Через меню **Repository → Open in Terminal** откройте корень проекта.
2. Остановите оба процесса API и Vite сочетанием Control+C в их терминалах. Не выполняйте импорт одновременно с редактированием в CMS.
3. Проверьте `node -v` и `npm -v`. Для проекта подходит Node.js 24.22+ в ветке 24 и npm из комплекта Node. Установите зависимости и проверьте сборку:

   ```sh
   npm ci
   npm run build
   ```

4. Если на компьютере уже есть база, отдельно сохраните резервную копию **до обновления/первого запуска API**:

   ```sh
   npm run db:backup -- "$HOME/Desktop/russkiy-sled-before-final-$(date +%Y%m%d-%H%M%S).sqlite"
   ```

   По умолчанию база — `.cms/content.sqlite`. Если раньше использовали `CMS_DB_PATH`, задайте тот же путь для резервного копирования, импорта и API. Новая чистая установка не требует копии несуществующей базы; обычный запуск API создаёт стартовую SQLite. При обновлении с очень старой CMS сначала выполните её обычное обновление по `ADMIN_GUIDE.md`, предварительно сохранив копию.

5. Посмотрите план без записи:

   ```sh
   npm run content:import -- --report "$HOME/Desktop/russkiy-sled-import-plan-$(date +%Y%m%d-%H%M%S).json"
   ```

   По умолчанию используется именно финальный файл из репозитория. План открывает существующую базу только для чтения. Если базы ещё нет, предварительная проверка проходит на временной базе и не создаёт пользовательскую SQLite. `conflicts: []` означает отсутствие конфликтов. `create + replaceSeed + skip` должно соответствовать пакету; реальный результат зависит от вашей базы.

6. При отсутствии конфликтов выполните импорт черновиков:

   ```sh
   npm run content:import -- --apply --report "$HOME/Desktop/russkiy-sled-import-result-$(date +%Y%m%d-%H%M%S).json"
   ```

   До открытия базы на запись команда автоматически создаст дополнительную консистентную копию в `.cms/backups/` с новым именем и правами 0600. Затем все операции выполняются одной транзакцией через штатное сохранение CMS. Ошибка отменяет всю транзакцию. Существующий файл отчёта не перезаписывается.

7. Запустите API:

   ```sh
   npm run server
   ```

   Во втором терминале, в том же каталоге:

   ```sh
   npm run dev -- --port 5173 --strictPort
   ```

8. В Safari откройте `http://localhost:5173/admin`. Для имеющегося владельца используйте прежний пароль. При первой установке создайте владельца командой `bash scripts/create-owner.sh` со скрытым вводом пароля по `ADMIN_GUIDE.md`. Импорт не создаёт и не сбрасывает пароль.
9. В словаре CMS выберите редакционный статус «Черновик». Сверьте 28 слов с `mapping` отчёта и откройте несколько статей: основную (например, матрёшку) и краткую (например, перестройку). Проверьте переключение языков, источники, выводы, сохранение и перезагрузку. Существующие URL сохраняются — у части дополнительных слов адрес останется прежним `word-…`; точный адрес есть в `mapping`.

## Если найден конфликт

Обычный импортёр ничего не перезаписывает и останавливает весь пакет. Причина и ID находятся в `conflicts`. Для защищённых активных статей используйте [отдельный режим согласования](IMPORT_REVIEW_GUIDE.md): предварительное сравнение по полям, код подтверждения владельца и транзакционная запись черновиков с сохранением прежних ID и публичных снимков. Команды безусловной принудительной перезаписи нет. Неоднозначные совпадения, архивные записи и конфликты справочников остаются заблокированными; для них требуется отдельное ручное сравнение. Не удаляйте статью ради повторного импорта, не сбрасывайте её версию и не удаляйте журнал. Повтор того же пакета после успешного импорта пропускается, включая записи, которые впоследствии редактировал владелец; изменённый пакет автоматически не заменяет предыдущий.

## Что проверить перед публикацией

Массив `editorialRestrictions[].scientificFields` отчёта перечисляет конкретные пути полей для всех 28 статей. Это исходный отчёт импорта, а не автоматически обновляемая экспертиза текущей базы.

- `languages[i].attestationStatus`: проверить точное написание, значение и соответствие языку по указанным источникам.
- `sources[ID].verifiedAt`: поставить дату **действительной** проверки источника. Не датировать непроверенную библиографию датой импорта. Для подтверждённой формы CMS требует проверенные источники для всех её `sourceIds`; оставьте там доказательства конкретной формы, а общую библиографию храните отдельно.
- `languages[i].correspondenceType`: определить, является ли форма заимствованием, переводом, собственным именем, культурным соответствием или другой формой. `borrowed` допускается только с подтверждённой формой и источниками.
- `originKind` и происхождение языковой карточки: проверить прямой/опосредованный/спорный маршрут. Особое внимание — интеллигенции, испанскому/португальскому «водка» и английскому `ukase`.
- `languages[i].ipa`: для исследовательских карточек нормативная транскрипция не установлена. Поле необязательно; не выдавайте реконструкции из архива за нормативное произношение.
- Армянские карточки калашникова, интеллигенции, погрома, спутника: составитель исключил их из потенциальных связей; нужно отдельно проверить имя, цитирование, перевод и нарицательное заимствование.
- Нидерландский портал содержит агрегированные данные; уровень доказательства отличается от академического словаря. Корпусная частотность всех научных карточек независимо не установлена.

Публикация текста с видимыми научными оговорками допускается существующей CMS и не равнозначна статусу подтверждённого заимствования. `publicationStatus=verified` и `scientificStatus=confirmed` нельзя ставить ради увеличения счётчиков; существующая серверная валидация остаётся включённой.

После проверки владелец может отметить нужные статьи в CMS и нажать **«Опубликовать выбранные»**, затем явно подтвердить пакетную операцию. Не выбирайте другие пользовательские черновики. Импортёр не публикует ничего и не содержит режима публикации. Для старых записей черновик сохраняет прежний публичный снимок до отдельной публикации владельцем; новые слова до публикации не видны.

Публичный сайт: `http://localhost:5173/`. В `/research` по умолчанию остаются восемь слов и три языка. В поле **«Область сравнения» → «Общий словарь»** доступны все опубликованные словарные формы и их языки. На карте нет постоянных подписей стран. Связи и показатели считаются по опубликованным проверенным данным; 60 потенциальных связей из файла не подставляются в статистику. После импорта неподтверждённых черновиков новых подтверждённых связей не появится.

## Данные и откат

Переносить облачную базу поверх базы MacBook не нужно: получите код и финальный JSON через GitHub и выполните импорт локально. Полная резервная копия SQLite содержит пароль владельца в виде хеша и пользовательские записи; храните её отдельно от репозитория. После дальнейшей работы дополнительно сохраните загруженные медиа (они находятся в SQLite).

Для отката остановите оба сервера, сохраните отдельную копию текущей базы и запустите API с `CMS_DB_PATH`, указывающим на **рабочую копию** резервного файла, по инструкции восстановления в `ADMIN_GUIDE.md`. Не заменяйте открытую SQLite и не удаляйте её WAL-файлы вручную. Восстановление старой базы отменит более поздние правки, поэтому сначала сохраните их отдельно. Изменений схемы в этом импорте нет; откат кода не требует отката базы.
